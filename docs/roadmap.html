      Mission and session decisions

      Our 20 November networking session established two requirements in Jeremy's own words:

      "Its supposed to be local, work when internet fails, peer to peer the whole shebang"

      "we must not lose sight over the mission and we must not compromise on security either"

      The same session rejected building a company that stores everyone's information on a VPS. The architecture already records the wider direction: modular roles, infrastructure of the user's choosing, and one shared protocol from personal calls to organisation-provided capacity. This roadmap carries those decisions forward. New release allocations and numerical test targets below are proposals; they are not additional decisions attributed to Jeremy.

      On 23 November, Jeremy clarified that other applications should be able to use Veil as their call provider, naming Mailcraft, Discord and Slack as examples. Embeddability is therefore a core product requirement. Compatibility with any particular third-party extension API is a separate adapter feasibility question, not something the existence of a Rust library proves.

      Decision Product consequence What must not happen
      Local operation is a primary mode Starting and joining on a reachable LAN must work with WAN and DNS unavailable A saved internet hostname prevents a local call from starting
      Devices own identity and relationships Keys and verified contacts stay locally controlled; export/recovery needs its own design A central account or contact upload becomes necessary to call
      Helpers are optional and replaceable A home PC, chosen community node or organisation node can supply a role Veil's own infrastructure becomes a hidden dependency
      Connectivity and trust are separate Discovery and route recovery still enforce identity, admission and current membership Finding a device or resuming a socket silently grants access
      Security bounds convenience Limits, consent and understandable failures are part of every connection feature A fallback disables pinning, encryption, privacy choices or removal
      One protocol serves every deployment Add roles/adapters and capacity without splitting the personal and enterprise products An enterprise fork quietly changes the trust model
      Other apps can use Veil as their call provider Offer a documented engine/SDK and provider contract; the standalone app exercises the same path Every integration copies the app's private engine or creates a new call protocol

      On 24 November, Jeremy selected strict helper targeting: use independently known peer endpoints, otherwise the chosen relay. The private TRUST-02 candidate applies this before automatic punch packets, rather than relying on a later key check to justify the first dial.

      The everyday experience we are building toward

      Alex starts a call on a laptop. Sam joins from a phone over 5G using an invitation and waits for admission. If they can connect directly they do; if they need a helper, it is one they chose. Sam sees a comprehensible connection state without having to understand QUIC or NAT.

      Later, both use a router with its WAN cable disconnected. Local only, a full invitation and opt-in nearby discovery let them call without DNS, an account or an external service. If a network changes, Veil attempts bounded recovery using the same authorised identity. Removal still takes effect immediately. A working path and a valid member are separate requirements.

      For a larger call, a willing participant or a chosen node can forward sealed media. Capacity and reachability determine whether that helps. Moving to a forwarder must not misrepresent who can still hear the call or allow a member to impersonate another person's media.

      Success means

      • A new person can install, choose a name, share an invitation and reach the lobby without creating an account. A known contact's verification state survives restart.
      • A real multi-device local call works with WAN and DNS unavailable, with no attempted internet traffic under the documented Local only policy.
      • An internet call finds a permitted path where one exists, explains failure where none exists, and never relaxes trust checks to improve its success rate.
      • Sound and control remain usable before video is improved. Network recovery does not create duplicate membership or revive removed people.
      • Removing or replacing a helper does not destroy a user's identity or local relationships.
      • The protection claims match the actual supported platforms and tested conditions.

      Embeddable call platform

      What Modular Agnostic Shared means for integrations

      Modular: identity/storage, transport, discovery, session coordination, media, forwarding, policy and UI have explicit interfaces. An application can supply its own UI and supported device/storage adapters without reimplementing admission, encryption or membership.

      Agnostic: the engine is not coupled to Veil's window, one UI toolkit, one server operator or one host application's account model. Native Rust is the first integration surface; cross-language hosts need a deliberate binding or local process bridge. Browser support is a separate runtime/media design, not an automatic consequence of exporting an SDK.

      Shared: standalone Veil, Mailcraft and other adapters use the same supported core and interoperable protocol. They can share a call without sharing account databases. Shared code does not mean automatically shared private keys, contacts, microphone access or history.

      Proposed layers

      Layer Owns Must not require
      Security and protocol core Device authentication, invitations, MLS membership, revocation, frame protection and replay checks A GUI, central login or host-managed cryptographic state
      Call engine and SDK Session lifecycle, route policy, media orchestration, bounded commands/events, resource teardown VeilApp, egui screens, global application settings or an updater
      Platform adapters Permission-aware camera/audio, secure storage and lifecycle integration A separate wire protocol for each platform
      Provider adapter Maps the host's start/join/mute/admit/end actions and events into the SDK Access to another app's keys or exemption from admission rules
      Optional call UI Video surfaces, controls, roster, verification and connection states Replacement of the host's whole interface
      Host application Its user experience, authorised user actions, account mapping and data policy A Veil company account or automatic upload of its contacts

      Current veil-call already exposes reusable session components. However, the higher-level engine is private inside veil-app and coordinates app models/media; the Android library entry points launch the application UI. This is a foundation for an SDK, not a documented drop-in provider yet. Workspace packages are currently marked publish = false.

      Proposed provider contract

      These are responsibilities to design, not names of existing public SDK methods.

      Host request Engine obligation Observable result
      Create a call or consume an invitation Validate configuration and policy; create isolated session state Connecting/lobby/live states, actionable error, opaque session handle
      Admit, decline or remove a person Check coordinator authority and current membership Roster/epoch update; removed devices remain revoked
      Enable/disable microphone, camera or share Enforce OS permissions and explicit capture intent Actual device/capture state and failure reason, not merely a toggled UI
      Select devices or a receive/data policy Apply bounded media changes without corrupting the session Routing/quality state, device error or confirmation
      Set Local only or relay-only privacy Enforce the policy on all discovery/control/media paths Permitted route information and explicit incompatibility errors
      Verify a device Bind verification to its actual key through a trusted comparison flow Verification state/key-change events scoped to that identity
      Subscribe to state and render media Provide ordered/versioned events and bounded queues/surfaces Roster, lobby, media, recovery, route and terminal events
      Cancel, leave, unload plugin or close host Stop capture/tasks, release resources and discard session secrets A bounded terminal transition; no orphan microphone or background service

      Commands need cancellation, idempotency rules and typed failures. Events need ordering, backpressure, resynchronisation and thread-affinity rules. The SDK must own frame counters and epoch transitions; adapters must not reuse session secrets or manufacture sequence state. Concurrent sessions need explicit device arbitration and separate identity/storage namespaces.

      Integration modes and host examples

      Mode Use Dependency and boundary
      Native Rust SDK A host embeds the engine and supplies its own controls Host runs inside the trusted endpoint process and can access plaintext/memory
      Local provider process Another language talks to an isolated Veil engine using authenticated local IPC Authorise the caller, scope session handles, bound messages and clean up on host/provider crash
      Reusable UI surface Host uses supported call controls/video surfaces or opens the Veil call window Preserve visible capture, verification, membership and privacy indicators
      External app adapter Mailcraft or a platform-supported plugin maps its UX to the provider contract Verify that the host permits the required call actions, media surfaces and distribution
      Protocol gateway Interoperate with another call system when protocol bridging is necessary A decrypting bridge is a visible participant; preserve accurate end-to-end encryption claims

      Mailcraft reference journey: click Call inside the host, select/share a Veil invitation, reach the lobby, admit, talk, change devices and end the session. Join the same call from the standalone Veil app. Veil does not need the host's mailbox, address book or message history. The reference host is a proposed validation target, not an assertion that a Mailcraft integration is already authorised or implemented.

      Discord/Slack-style integrations: evaluate three distinct outcomes: launch a Veil call from a link, embed Veil's own call experience, or bridge into a platform's native calls. They have different APIs and trust implications. Do not promise native call-provider replacement before checking the current platform's documented extension points and permissions. An invite-launch integration is useful but does not alone satisfy the embedded-provider goal.

      Embedding security and compatibility

      An embedding app with media or process access is a participant endpoint, not a blind relay. It may observe or record plaintext; encryption cannot hide a user's call from software that captures or renders it. The SDK must document this trust boundary and avoid exposing secret keys when an opaque operation suffices. IPC limits authority but does not turn an untrusted application receiving decrypted media into a trusted one.

      Default identity stores should be scoped per host app. Reusing a person's Veil identity across apps requires explicit consent and a design for key custody, verification continuity and revocation; copying key files is not an integration strategy. Host account names are display metadata until explicitly bound to a verified device identity.

      Keep separate versions for the product milestone, public Rust API, IPC/binding schema and wire protocol. Publish a compatibility matrix and a deprecation window before calling the SDK stable. The 1.0 gate includes a supported provider contract and a standalone/embedded interop test. A third-party platform adapter need not be complete for every named example.

      Priority and delivery approach

      The critical path is review the integrated preview → prove independent local operation and safe recovery → widen permitted reach → preserve identity everywhere → strengthen group capacity and continuity. Security review, test evidence and diagnostics accompany every step.

      Priority Work Reason
      Now AND-02, SDK-01, TRUST-02, LOCAL-01, DIAG-01 and immediate TRUST-01 design Capture the existing work, define the provider boundary, defend expanded exposure, and prove the offline premise
      Next MOB-01, MOB-02, INVITE-01, DIST-01 Turn a successful connection into a usable repeatable phone/local experience
      Then SDK-02, NET-01, NET-02, NET-03, DATA-01, OPS-01 Expose the shared engine and widen permitted reach while preserving privacy choices
      Alongside platform work DESK-01, ID-01, TEST-01, BIND-01, EMBED-01 Stable identities, a cross-language boundary and a reference host prove shared use
      Before broad group claims TRUST-01, GROUP-01, MEDIA-01 Fix attribution and explicitly handle members a forwarder cannot serve
      Conditional extensions IOS-01, HOST-01, NEAR-01, MSG-01, SCALE-01, PERF-01, ORG-01 Extend the same model after feasibility, trust and resource limits are established

      This is a dependency order, not a rule that all work must be serial. Native storage can advance while transport designs are reviewed. No prerequisite should falsely imply that desktop networking requires an Android package. A small design/validation change belongs in its own reviewable increment; no milestone requires a single enormous implementation PR.

                                                          Data ownership and trust boundaries

                                                          The rule is: devices own people and conversations; helpers keep only the bounded routing state needed to make an authorised connection possible. "No central data company" does not mean helpers see no information. Their observable metadata and retention must stay explicit.

                                                          Data Intended owner/location Helper access and retention rule
                                                          Device private keys and verification state OS-protected storage on the user's device No upload to rendezvous, relay or forwarder
                                                          User-assigned contact names and relationships Local storage, with explicit user-controlled export if implemented No public directory, address book upload or social graph service
                                                          Call content and MLS state Authorised participants; current session state is in memory No helper receives content keys; persisted MLS recovery is a separate design
                                                          Conversation history, if enabled later Encrypted local storage with deletion/backup controls No automatic server archive
                                                          Full invitation Shared intentionally by the host; signed, expiring and single use A stolen invite can request entry, not bypass admission
                                                          Sealed short invitation Temporary bounded storage on a chosen rendezvous Helper retains ciphertext and routing metadata; full invites remain the offline option
                                                          Discovery beacon Opt-in local broadcast using temporary service identity No names, permanent identity, roster or invitation secret in public beacons
                                                          Node identity and configured host grants Operator-controlled key/config files, including the persistent hosts allow-list Keep the node's own private key local; explicit grant/revocation and retention policy
                                                          Helper registrations and routing state Bounded helper memory for an active registration Expire stale state; recheck configured grants; disclose identifiers/IP addresses the role must observe
                                                          Media in transit Sealed participant frames in bounded transient buffers No disk recording or content analysis as part of a relay/forwarder role
                                                          Diagnostics Local redacted logs, exported explicitly by the user No silent telemetry or automatic log upload; no keys or reusable invite secrets

                                                          A malicious helper can keep a record despite a RAM-only implementation. Trust minimisation reduces what it can learn; it cannot make its network observations disappear. Padding and temporary connection identifiers require separate designs and measured overhead.

                                                          Integration quality Public versus private API use, host dependencies, cancellation/crash leaks Whether the SDK is reusable rather than a wrapper around the full app
                                                          Privacy Attributable destinations, beacon fields, helper metadata and exported logs Whether selected privacy modes and data-minimisation rules hold

                                                          Do not set a global call-success percentage from one device pair. Establish repeatable baselines across the defined scenarios, then set performance thresholds against those conditions. The proposed 10-second interruption, 20-second recovery and 30-minute soak gates are starting acceptance targets; changing them requires a documented supported-behaviour decision and updated tests, not quietly lowering the bar after a failed run.

                                                          Release gates and deliverables

                                                          Every milestone has a small set of reviewable deliverables. A successful demo advances the evidence; it does not silently close storage, revocation, lifecycle or integration requirements.

                                                          Target Required deliverables Explicit release blocker
                                                          0.1.14 Android integration reviews, pinned build instructions/CI, existing desktop checks, engine/provider ADR and API inventory Unexplained native lifetime ownership, unreproducible build or accidental desktop regression
                                                          0.2.0 Offline hardware report, integrated convenience-path review, mobile/audio scenarios, QR/manual join checks, redacted diagnostics, signed preview/upgrade record Removed-member recovery, weakened pinning/privacy, capture left running after leave or core offline call depending on WAN
                                                          0.3.0 Consumable headless Rust sample, desktop/Android engine migration, full TCP joining path, independent helper tests, measured receive controls and node load limits GUI dependency in the SDK, UDP-only joining on the TCP path, unbounded retry/queue behaviour or privacy-leaking route upgrade
                                                          0.4.0 Native persistence matrix, host-scoped identity design, versioned authorised local bridge, reference embedded app and standalone interop report Silent identity regeneration, unauthorised local IPC, plugin unload leaving capture alive or required central host data upload
                                                          0.5.0 Sender-attribution/replay review, measured group media, forwarding partial-failure decision, active-node outage results Another member accepted as a different media sender, hidden participants without media or unbounded group resource use
                                                          1.0.0 Defined supported scope, independent review/findings disposition, API/protocol compatibility policy, full mandatory matrix, signed distribution and maintenance process Any unresolved issue classified as release-blocking in the reviewed threat model or a protection claim unsupported on a supported path

                                                          Before a release candidate, classify findings by exploitability, exposure and user impact, record remediation or a justified scoped exclusion, and keep security reports private as required. A known high-impact trust bypass is not made acceptable by labelling the package beta. If a platform/path is excluded, the product and documentation must make that boundary visible and fail safely rather than quietly offering the unsupported behaviour.

                                                          Earlier group previews: TRUST-01's allocation to 0.5 is a completion deadline, not permission to defer a release-blocking attribution flaw. Before any earlier preview including forwarding, classify the known malicious-member weakness and either fix it or enforce a documented scope restriction where it is release-blocking. A five-device engineering test may exercise that path with cooperating test participants; it does not establish safe use with untrusted members. The 0.2 supported experience must name this boundary, including any disabled/group-limited path. If no safe enforceable scope is accepted, TRUST-01 moves onto that release's critical path.

                                                          Principles and product definition

                                                          Updated 23 November 2026. Proposed milestones for maintainer review; versions are planning targets, not release dates or changes to the current package version.

                                                          Modular. Agnostic. Shared. Veil is a video and audio calling app and a reusable call engine/provider that other applications can embed. Its standalone app is a first-party client of the same calling capabilities offered to integrators.

                                                          Veil's goal is familiar, dependable private communication where people own their identities, contacts and conversation data, calls are peer to peer by default, and a surviving local network remains useful when the internet fails. People may add their own computers or chosen nodes for reach and capacity. Those helpers must be replaceable and receive no conversation keys.

                                                          The product should feel as approachable as a conventional calling app without requiring a company account, company contact directory or company-operated call infrastructure. Easier connection must preserve strict admission, verification and revocation. Android delivery is part of reaching people; it is not the whole mission.

                                                          • Keep the shared Rust call engine and protocol across desktop and mobile.
                                                          • Keep calls end-to-end encrypted and servers chosen by the user. No built-in public node, accounts or telemetry are required by this roadmap.
                                                          • Describe a capability by the user outcome, its dependencies and evidence of completion. A compiled implementation, a local hardware test and an internet call establish different things.
                                                          • Treat security fixes as immediate work across milestones. A future audit does not defer fixing a known weakness.
                                                          • Finish and validate a useful increment before widening its platform or performance scope.

                                                          Version and compatibility rules

                                                          • Continue the existing 0.1.x preview line for consolidation/fixes; 0.1.14 is an integration target, not a stable mobile promise. After 0.2.0, use patch releases for compatible fixes and minor releases for capability milestones or deliberate pre-1.0 compatibility breaks.
                                                          • Give testers prereleases such as 0.2.0-alpha.1 and 0.2.0-beta.1. The current 0.1.13-mobile.3 label is a development preview, not a separate protocol generation.
                                                          • Record wire, invitation, node and persisted-data compatibility separately in every release. Matching version numbers alone are not evidence that two builds interoperate. A wire break must name the minimum compatible clients/nodes and whether fresh invitations are required.
                                                          • At 1.0, establish the supported public protocol/API surface. Compatible fixes use patch versions, compatible additions use minor versions, and incompatible changes use major versions.
                                                          • Track the Rust SDK, IPC/binding schema, host adapter and wire protocol explicitly. Product milestones do not promise those interfaces share one version or compatibility window. Publish tested combinations and a deprecation policy; never hide a protocol break inside a supposedly compatible host-plugin update.
                                                          • Never move a published tag. Allocate actual release numbers only after checking existing tags/releases. This roadmap does not change Cargo or Android versions.

                                                          Work after the core milestones

                                                          QR camera scanning is now in the proposed 0.2 INVITE-01 scope. Android screen sharing remains a separately scoped platform extension. IOS-01 is conditional on hardware/tooling; HOST-01, NEAR-01, MSG-01, SCALE-01, PERF-01 and ORG-01 have design gates but no reserved version. Allocate their release numbers after feasibility and scope decisions instead of implying a fixed serial path to 0.7/0.8/0.9. Their absence does not remove the requirement for a reusable engine/provider in the core baseline.

                                                          Maintaining the roadmap

                                                          Every Veil session begins by opening the live roadmap and reading its highlighted next step. Follow the session workflow and tracking guide. Record meaningful work transitions in roadmap-state.json with tools/roadmap.py; the live preview polls that recorded state and refreshes document changes. A file-based HTML copy is a saved snapshot, clearly distinguished from the live local view.

                                                          Use the capability ID in an issue or PR and link it here when work starts. Mark a capability complete only when its exit evidence is recorded, with the build/commit, platform, network, result and remaining limits. A test report should also distinguish user-reported results from automated checks and identify direct/punched/relayed/forwarded paths when known. Do not record private keys or reusable invitation secrets.

                                                          When scope changes, update the milestone and dependency together. Keep completed test evidence instead of turning it back into a task. Move shipped behaviour to the changelog and refresh the handoff; keep capability IDs stable so older discussions remain meaningful.
